# Функциональные требования

Требования сформулированы как проверяемые утверждения «Система должна…». Каждое привязано к истории,
сервису-владельцу и элементу контракта. Все требования этого документа реализованы в прототипе.

## Управление отправлениями (shipment-service)

| ID | Требование | История | Контракт |
|----|------------|---------|----------|
| FR-01 | Система должна принимать запрос на создание отправления с атрибутами: внешний номер заказа, постамат, размер посылки, получатель (имя, телефон E.164, e-mail — необязательно), тип и сумма оплаты | US-01 | `POST /api/v1/shipments` |
| FR-02 | Система должна аутентифицировать партнёра по API-ключу в заголовке `X-API-Key` и отклонять запросы заблокированных партнёров | US-01 | `401`, `403` |
| FR-03 | Система должна обеспечивать идемпотентность создания по заголовку `Idempotency-Key` в рамках партнёра | US-01 | `Idempotent-Replayed`, `422` |
| FR-04 | Система должна отклонять создание отправления с уже существующим у партнёра внешним номером заказа | US-01 | `409 DUPLICATE_EXTERNAL_ORDER` |
| FR-05 | Система должна возвращать отправление и список отправлений партнёра с фильтрами по статусу и внешнему номеру, с постраничной выдачей | US-02 | `GET /shipments`, `GET /shipments/{id}` |
| FR-06 | Система должна вести и отдавать историю смен статуса с указанием инициатора и причины | US-02 | `GET /shipments/{id}/history` |
| FR-07 | Система должна отменять отправление по запросу партнёра в статусах `CREATED` и `CELL_RESERVED` | US-03 | `POST /shipments/{id}/cancel` |
| FR-08 | Система должна менять статус отправления только по разрешённым переходам | все | [state-machines](../03-architecture/state-machines.md) |
| FR-09 | Система должна устанавливать срок хранения при закладке и автоматически переводить отправление в `EXPIRED` по его истечении | US-10 | событие `shipment.expired` |
| FR-10 | Система должна предоставлять публичное отслеживание без персональных данных | US-09 | `GET /api/v1/tracking/{id}` |
| FR-11 | Система должна позволять оператору досрочно завершить хранение | US-14 | `POST /internal/v1/shipments/{id}/expire` |

## Постаматы и ячейки (locker-service)

| ID | Требование | История | Контракт |
|----|------------|---------|----------|
| FR-12 | Система должна отдавать список постаматов с фильтром по городу и количеством свободных ячеек каждого размера | US-04 | `GET /api/v1/lockers` |
| FR-13 | Система должна резервировать для нового отправления наименьшую подходящую свободную ячейку; при невозможности — сообщать причину отказа | US-01 | события `locker.cell.reserved`, `locker.cell.reservation_failed` |
| FR-14 | Система должна гарантировать, что одна ячейка не будет зарезервирована за двумя отправлениями при параллельных запросах | US-01 | — |
| FR-15 | Система должна освобождать ячейку при отмене отправления и при истечении срока резерва | US-03, US-12 | события `locker.cell.released`, `locker.reservation.expired` |
| FR-16 | Система должна регистрировать закладку посылки и генерировать код получения | US-05 | `POST /lockers/{id}/deposits` |
| FR-17 | Система должна выдавать посылку по верному коду, если оплата не требуется или получена | US-07 | `POST /lockers/{id}/pickups` |
| FR-18 | Система должна считать неверные вводы кода и блокировать ввод после пяти подряд | US-07 | `403`, `429` + `Retry-After` |
| FR-19 | Система должна регистрировать изъятие посылки с истёкшим сроком хранения | US-11 | `POST /lockers/{id}/returns` |
| FR-20 | Система должна позволять оператору снять блокировку ввода кода | US-13 | `POST /internal/v1/lockers/{id}/unblock` |

## Платежи (payment-service)

| ID | Требование | История | Контракт |
|----|------------|---------|----------|
| FR-21 | Система должна открывать счёт для каждого отправления с оплатой при получении и закрывать его при отказе, отмене и истечении срока хранения | US-08, US-10 | события `shipment.*` |
| FR-22 | Система должна создавать платёж в PSP на сумму счёта и возвращать ссылку на платёжную страницу | US-08 | `POST /api/v1/payments` |
| FR-23 | Система должна обеспечивать идемпотентность создания платежа и не допускать двух незавершённых платежей по одному счёту | US-08 | `Idempotency-Key`, `200` |
| FR-24 | Система должна принимать уведомления PSP, проверяя подпись HMAC-SHA256, сумму и валюту | US-08 | `POST /api/v1/webhooks/psp` |
| FR-25 | Система должна обрабатывать повторные уведомления PSP без побочных эффектов и вести их журнал | US-08 | `psp_webhook_log` |
| FR-26 | Система должна возвращать состояние платежа | US-08 | `GET /api/v1/payments/{id}` |

## Уведомления (notification-service)

| ID | Требование | История | Контракт |
|----|------------|---------|----------|
| FR-27 | Система должна отправлять получателю SMS при событиях: готово к выдаче, оплата получена, выдано, срок хранения истёк | US-06 | события `shipment.*` |
| FR-28 | Система должна отправлять не более одного сообщения на одно событие, в том числе при повторной доставке события | US-06 | `UNIQUE (event_id, channel)` |
| FR-29 | Система должна хранить журнал отправленных сообщений и отдавать его по идентификатору отправления | US-15 | `GET /api/v1/notifications` |

## Сквозные требования

| ID | Требование | Контракт |
|----|------------|----------|
| FR-30 | Все ошибки API должны возвращаться в формате RFC 7807 с машиночитаемым кодом | [каталог ошибок](../05-integration/error-catalog.md) |
| FR-31 | Каждый запрос и порождённые им события должны нести сквозной идентификатор корреляции | заголовок `X-Correlation-Id`, поле `correlationId` |
| FR-32 | Изменение данных сервиса и публикация события об этом изменении должны быть атомарны | [ADR-0005](../03-architecture/adr/0005-outbox-and-idempotent-consumer.md) |
