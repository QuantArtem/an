# ADR-0005. Transactional outbox и идемпотентный потребитель

**Статус:** принято · **Затрагивает:** FR-32, NFR-08, NFR-12, NFR-14

## Контекст

Сервис должен изменить данные в своей БД **и** опубликовать событие. Это две разные системы, общей
транзакции у PostgreSQL и Kafka нет. Возможные сбои:

- данные сохранены, сервис упал до отправки события → другие сервисы никогда не узнают (ячейка
  не будет зарезервирована, оплаченный заказ не откроется);
- событие отправлено, транзакция БД откатилась → другие сервисы отреагируют на то, чего не было.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Отправка в Kafka после COMMIT** | Просто | Потеря события при сбое между COMMIT и отправкой |
| **B. Отправка в Kafka до COMMIT** | Просто | «Фантомное» событие при откате |
| **C. Transactional outbox + опрос таблицы** | Атомарность средствами одной БД; не нужны дополнительные компоненты | Задержка на интервал опроса; нагрузка на БД; доставка at-least-once |
| **D. Transactional outbox + CDC (Debezium)** | Нет опроса, минимальная задержка | Дополнительная инфраструктура (Kafka Connect), сложнее эксплуатация |
| **E. Event sourcing** | События — единственный источник истины | Радикально меняет модель хранения, избыточно для задачи |

## Решение

**Публикация — вариант C.** Событие записывается в таблицу `outbox` в той же транзакции, что и
бизнес-данные. Фоновый процесс (relay) раз в 200 мс читает неопубликованные записи
(`FOR UPDATE SKIP LOCKED` — безопасно при нескольких экземплярах), отправляет в Kafka с `acks=all`
и проставляет `published_at`.

**Потребление — идемпотентный потребитель.** Доставка at-least-once означает возможные дубли, поэтому:

1. offset фиксируется вручную, **после** успешной обработки;
2. обработка события и вставка его `eventId` в таблицу `processed_events` выполняются в одной
   транзакции; конфликт по первичному ключу означает «уже обработано — пропустить»;
3. обработчик вызывается до 3 раз с нарастающей паузой; затем событие отправляется в топик
   `lockerflow.dlq`, а потребитель продолжает работу.

Реализация — `libs/lf_common/events.py`, схема — [SD-07](../sequences.md).

## Последствия

- ➕ Событие публикуется тогда и только тогда, когда изменение данных зафиксировано.
- ➕ Повторная доставка не приводит к повторным побочным эффектам (проверено: дубль webhook в TC-02
  не порождает второго SMS).
- ➖ Задержка публикации до 200 мс — приемлемо для NFR-03/NFR-04.
- ➖ Таблицы `outbox` и `processed_events` растут → нужна регламентная очистка (записи старше 7 суток).
- ➖ Событие в DLQ нарушает порядок для своего отправления → разбор DLQ — ручная операция с алертом
  (NFR-14, NFR-29).

**Условие пересмотра:** при нагрузке, на которой опрос outbox заметно нагружает БД, перейти
на CDC (вариант D) — формат событий и потребители при этом не меняются.
