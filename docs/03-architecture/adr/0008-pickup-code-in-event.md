# ADR-0008. Передача кода получения в событии

**Статус:** принято, с планом пересмотра · **Затрагивает:** BR-07, NFR-18, NFR-24

## Контекст

Код получения генерирует `locker-service` (он же его проверяет). Отправить код получателю должен
`notification-service`, а телефон получателя знает только `shipment-service`. Код нужно как-то
доставить от первого к третьему.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Код в полезной нагрузке события** (`locker.parcel.deposited` → `shipment.ready_for_pickup`) | Просто; нет синхронных вызовов; уведомление формируется из одного события | Секрет в открытом виде лежит в Kafka весь срок хранения топика и виден всем, кто может читать топик |
| **B. Синхронный запрос кода** (`notification` → `locker`) | Код не попадает в брокер | Синхронная зависимость; `locker` должен хранить код в обратимом виде, а не хэш |
| **C. Код генерирует `notification`** и сообщает `locker` только хэш | Открытый код существует только в одном сервисе | Перевёрнутая ответственность: сервис уведомлений становится участником контроля доступа к ячейке |
| **D. Шифрование поля** (envelope encryption, ключ есть только у `locker` и `notification`) | Код в брокере нечитаем для остальных | Управление ключами, усложнение отладки |

## Решение

Для MVP — вариант **A** со смягчающими мерами:

1. в БД `locker-service` хранится только HMAC кода с секретным «перцем» — утечка базы не раскрывает
   действующие коды;
2. код одноразовый и живёт не дольше срока хранения (72 часа);
3. перебор ограничен блокировкой (BR-08);
4. ACL Kafka: читать `shipment.events` и `locker.events` могут только сервисы LockerFlow (NFR-21,
   в прототипе не настроено);
5. срок хранения сообщений в этих топиках — 7 суток.

## Последствия

- ➖ Код в открытом виде присутствует в двух топиках и в журнале уведомлений (`notifications.body`).
  В прототипе это ещё и способ «прочитать SMS» в e2e-тестах; в промышленной версии текст в журнале
  должен маскироваться (NFR-24).
- ➖ Любой сервис с доступом на чтение топика может получить действующие коды.

**План пересмотра:** перейти к варианту D до подключения к шине сторонних потребителей (аналитика,
партнёрские интеграции) — формат события при этом не меняется, меняется только представление поля.
