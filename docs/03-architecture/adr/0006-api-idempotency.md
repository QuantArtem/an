# ADR-0006. Идемпотентность модифицирующих запросов API

**Статус:** принято · **Затрагивает:** FR-03, FR-23, FR-25, BR-10

## Контекст

Сеть ненадёжна: клиент может не получить ответ на `POST` и повторить запрос. Без защиты это приводит
к двум отправлениям на один заказ (две занятые ячейки) или к двум платежам (двойное списание).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Только естественный ключ** (`externalOrderId`) | Не требует от клиента ничего нового | Повтор получает `409` вместо исходного ответа — клиент должен отдельно запрашивать результат; не у каждой операции есть естественный ключ |
| **B. `PUT` с идентификатором, сгенерированным клиентом** | Идемпотентность по семантике HTTP | Клиент управляет идентификаторами системы; не подходит для платежей |
| **C. Заголовок `Idempotency-Key`** | Универсально; повтор возвращает исходный результат; де-факто стандарт платёжных API | Нужно хранить ключи и решать, что делать при совпадении ключа с другим телом |

## Решение

Вариант **C** для `POST /shipments` и `POST /payments`, **дополнительно** — естественные ключи как
вторая линия защиты.

| Ситуация | Поведение |
|----------|-----------|
| Заголовок отсутствует | `400 IDEMPOTENCY_KEY_REQUIRED` — ключ обязателен, чтобы клиент не мог «забыть» про идемпотентность |
| Ключ новый | Операция выполняется, ключ сохраняется в той же транзакции |
| Ключ известен, запрос тот же | Возвращается ранее созданный ресурс, заголовок `Idempotent-Replayed: true` |
| Ключ известен, запрос другой | `422 IDEMPOTENCY_KEY_REUSED` — ошибка клиента, молча возвращать чужой результат опасно |
| Два одинаковых запроса одновременно | Сериализуются: advisory-блокировка по ключу (shipment), блокировка строки счёта (payment) |

Сравнение запросов: в `shipment` — по SHA-256 от нормализованного тела; в `payment` — по `shipmentId`.

Вторая линия защиты:

- `UNIQUE (partner_id, external_order_id)` → `409 DUPLICATE_EXTERNAL_ORDER` с идентификатором существующего отправления;
- не более одного `PENDING`-платежа по счёту (BR-10) — возвращается существующий;
- webhook PSP дедуплицируется по `eventId` уведомления.

Операции, идемпотентные по своей природе, ключа не требуют: повторная отмена возвращает `200`,
повторная закладка — `409` с текущим статусом резерва.

## Последствия

- ➕ Клиент может безопасно повторять любой запрос до получения ответа.
- ➖ Ключи нужно хранить; срок хранения — 24 часа, после чего защита остаётся на естественных ключах
  (очистка — регламентное задание, в прототипе не реализовано).
- ➖ Операции терминала (закладка, выдача) защищены только статусной моделью — этого достаточно,
  так как повтор после успеха даёт однозначный `409`/`403`, но ответ отличается от исходного.
