# ADR-0003. Асинхронное взаимодействие сервисов через Kafka

**Статус:** принято · **Затрагивает:** NFR-08…NFR-10, NFR-12, NFR-13

## Контекст

Сервисам нужно сообщать друг другу об изменениях. Требования: не терять сообщения, сохранять порядок
изменений одного отправления, не создавать цепочек синхронных зависимостей.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Синхронный REST между сервисами** | Простая модель «запрос — ответ», мгновенная согласованность | Временная связность: доступность цепочки = произведение доступностей (0,999³ ≈ 0,997); каскадные таймауты; повторы нужно реализовывать самостоятельно |
| **B. RabbitMQ (очереди)** | Гибкая маршрутизация, проще в эксплуатации | Сообщение удаляется после прочтения — нельзя переиграть историю и подключить нового потребителя «с начала»; порядок при нескольких потребителях не гарантируется |
| **C. Apache Kafka (журнал событий)** | Порядок в пределах ключа; хранение и повторное чтение; независимые группы потребителей; высокая пропускная способность | Сложнее эксплуатация; только at-least-once без дополнительных мер; нет отложенных сообщений из коробки |

## Решение

Вариант **C** для всех взаимодействий между сервисами LockerFlow. Синхронный REST остаётся только
на внешних границах (партнёры, терминалы, PSP, SMS).

Соглашения:

| Параметр | Значение | Почему |
|----------|----------|--------|
| Топики | По одному на контекст-издатель: `shipment.events`, `locker.events`, `payment.events` | Все события агрегата — в одном топике, значит, упорядочены между собой |
| Ключ сообщения | `shipmentId` | Все события одного отправления попадают в одну партицию → обрабатываются по порядку |
| Партиции | 3 на стенде | Параллелизм потребителей; в промышленной среде — по расчёту нагрузки |
| Формат | JSON в едином конверте (`eventId`, `eventType`, `eventVersion`, `occurredAt`, `source`, `correlationId`, `key`, `payload`) | Читаемость; схема зафиксирована в AsyncAPI |
| Именование событий | `<контекст>.<сущность>.<факт в прошедшем времени>` | Событие — свершившийся факт, а не команда |
| Группы потребителей | Имя сервиса (`locker-service` и т. д.) | Каждый сервис получает каждое событие ровно в одном экземпляре |
| Версионирование | Поле `eventVersion`; добавление необязательных полей — без смены версии | Обратная совместимость потребителей |

## Последствия

- ➕ Сервис-издатель не знает своих потребителей: `notification` подключён без изменений в `shipment`.
- ➕ Остановленный потребитель дочитывает пропущенное после запуска (NFR-08).
- ➖ Партнёр получает `202 Accepted`, а не итоговый результат → нужен опрос или webhook.
- ➖ Дубли неизбежны → все потребители идемпотентны (ADR-0005).
- ➖ «Ядовитое» сообщение может остановить партицию → повторы и DLQ.
