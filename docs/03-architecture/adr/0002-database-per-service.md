# ADR-0002. Отдельная база данных на сервис

**Статус:** принято · **Затрагивает:** NFR-08, NFR-33

## Контекст

Нужно решить, как сервисы получают доступ к данным друг друга: `locker` должен знать, оплачено ли
отправление; `payment` — сумму к оплате; `shipment` — номер ячейки.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **A. Общая БД, общие таблицы** | JOIN и транзакции «из коробки» | Схема становится неявным общим контрактом: изменение таблицы ломает чужой сервис; нет изоляции нагрузки и отказов |
| **B. Общий сервер, отдельные схемы, чтение чужих схем запрещено** | Дешевле в эксплуатации | Запрет держится только на дисциплине |
| **C. Отдельная БД и учётная запись на сервис** | Физическая невозможность обойти контракт; независимое масштабирование и миграции | Нет JOIN между контекстами; нужны проекции данных и итоговая согласованность |

## Решение

Вариант **C**. На стенде — один экземпляр PostgreSQL с четырьмя базами и четырьмя пользователями
(`deploy/init-databases.sql`); в промышленной среде — отдельные кластеры.

Правила:

1. Ссылки на сущности других сервисов хранятся как идентификаторы **без внешних ключей**
   (`shipments.locker_id`, `reservations.shipment_id`).
2. Нужные чужие данные сервис хранит у себя как **проекцию**, обновляемую по событиям
   (таблица владения — в [service-decomposition.md](../service-decomposition.md)).
3. Запрос «собрать всё по отправлению» для поддержки решается на уровне API (композиция),
   а аналитика — выгрузкой событий в хранилище, но не чтением чужих баз.

## Последствия

- ➕ Схему сервиса можно менять без согласования с другими командами.
- ➕ `locker` принимает решение о выдаче без сетевых вызовов.
- ➖ Проекция может отставать (окно — NFR-15).
- ➖ Нужен сверочный отчёт между сервисами (таблица соответствия статусов — в
  [state-machines.md](../state-machines.md)).
