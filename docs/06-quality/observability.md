# Наблюдаемость и эксплуатация

> В прототипе реализованы сквозной correlation id, структурированные по смыслу логи, health-check'и и DLQ.
> Метрики, алерты и трассировка **спроектированы** в этом документе как требования к промышленной версии
> (NFR-26…NFR-30).

## Как найти, что случилось с заказом

Главный сценарий поддержки — «покупатель оплатил, а ячейка не открывается».

1. Взять `correlationId` из ответа API (заголовок `X-Correlation-Id` или поле тела ошибки) либо
   найти отправление по `externalOrderId`.
2. `GET /api/v1/shipments/{id}/history` — на каком шаге остановился жизненный цикл.
3. `GET /api/v1/notifications?shipmentId=` — что было отправлено получателю.
4. Поиск по `correlationId` в логах всех сервисов: один идентификатор связывает исходный запрос
   и обработку порождённых им событий.
5. Если событие не обработано — проверить топик `lockerflow.dlq` и таблицу `outbox` издателя.

```bash
docker compose logs | grep "corr=<correlationId>"
```

## Логи

| Требование | Реализация |
|------------|------------|
| Каждая запись обработки события содержит `eventType`, ключ и `correlationId` | ✅ `event handled type=… key=… corr=…` |
| Отклонённый переход статуса фиксируется с уровнем WARNING | ✅ `transition X -> Y ignored for <id>` |
| Ошибка обработчика — с трассировкой стека и номером попытки | ✅ |
| Формат JSON, сбор в централизованное хранилище | 📐 |
| Персональные данные и коды получения не попадают в логи | 🟡 заглушка SMS пишет текст сообщения — только для стенда |

## Метрики (целевые)

### Технические — по методу RED на каждый сервис

| Метрика | Тип | Метки |
|---------|-----|-------|
| `http_requests_total` | счётчик | `service`, `route`, `method`, `status` |
| `http_request_duration_seconds` | гистограмма | `service`, `route` |
| `events_published_total` / `events_consumed_total` | счётчик | `service`, `event_type`, `result` |
| `event_handling_duration_seconds` | гистограмма | `service`, `event_type` |
| `outbox_unpublished_count`, `outbox_oldest_unpublished_age_seconds` | индикатор | `service` |
| `kafka_consumer_lag` | индикатор | `group`, `topic`, `partition` |
| `dlq_messages_total` | счётчик | `consumer`, `event_type` |

### Бизнес-метрики — связаны с целями из Vision

| Метрика | Формула | Цель |
|---------|---------|------|
| Доля отклонённых отправлений | `REJECTED / все созданные`, в разрезе постамата и причины | Сигнал к расширению постамата (риск переполнения) |
| Время от закладки до выдачи | `DELIVERED.at − READY_FOR_PICKUP.at`, медиана | BG-2: ≤ 24 ч |
| Доля невостребованных | `EXPIRED / READY_FOR_PICKUP` | Контроль BG-2 |
| Конверсия оплаты | `успешные платежи / созданные платежи` | BG-3; падение — сигнал о проблемах у PSP |
| Длительность саги резервирования | `CELL_RESERVED.at − CREATED.at`, p95 | NFR-03: ≤ 5 с |
| Задержка «оплата → разрешение выдачи» | от `payment.succeeded` до обработки `shipment.paid` в locker-service, p95 | NFR-04: ≤ 5 с |
| Заполненность постамата | `занятые и зарезервированные ячейки / все`, по размерам | Планирование сети |
| Блокировки ввода кода | число событий `PICKUP_BLOCKED` на постамат в сутки | Выявление попыток подбора |

Все бизнес-метрики вычисляются из потока событий — отдельной доработки сервисов не требуется.

## Алерты (целевые)

| Алерт | Условие | Критичность | Действие дежурного |
|-------|---------|-------------|--------------------|
| Сообщение в DLQ | `dlq_messages_total` вырос | Высокая | Найти событие, устранить причину, переотправить; пока событие в DLQ, отправление «зависло» |
| Outbox не публикуется | возраст старейшей неопубликованной записи > 30 с | Высокая | Проверить доступность Kafka и процесс relay |
| Отставание потребителя | `kafka_consumer_lag` > 1000 дольше 5 минут | Высокая | Проверить сервис-потребитель, при необходимости масштабировать |
| Ошибки API | доля `5xx` > 1 % за 5 минут | Высокая | — |
| Деградация PSP | доля `PSP_UNAVAILABLE` > 5 % за 5 минут | Средняя | Связаться с PSP; выдача предоплаченных заказов не затронута |
| Зависшие отправления | `CREATED` дольше 5 минут | Средняя | Сага не завершилась: проверить locker-service и DLQ |
| Расхождение статусов | сверочный отчёт нашёл несоответствие (таблица в [state-machines.md](../03-architecture/state-machines.md)) | Средняя | Разбор вручную |
| Невостребованные возвраты | `EXPIRED` дольше 48 часов | Низкая | Напомнить курьерской службе |

## Разбор сообщения из DLQ

Формат сообщения: `{"consumer": "<группа>", "event": { …исходный конверт… }}`.

1. Определить причину по логам потребителя (`handler failed type=… attempt=…`).
2. Устранить причину (ошибка в коде, отсутствующие справочные данные).
3. Повторно опубликовать исходный конверт в исходный топик **с тем же `eventId` и ключом**.
   Запись в `processed_events` не создавалась (транзакция откатилась), поэтому событие будет обработано.
4. Убедиться, что отправление продвинулось по статусам.

Ограничение: на время разбора порядок событий этого отправления нарушен — последующие события могли
быть обработаны раньше и отклонены статусной моделью. После переотправки проверить историю статусов.
